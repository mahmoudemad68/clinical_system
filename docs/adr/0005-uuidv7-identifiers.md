# ADR 0005 — UUIDv7 primary keys, no public sequential identifiers

- **Status:** Accepted
- **Date:** 2026-08-24
- **Deciders:** Platform architecture, PostgreSQL consistency, backend, security
- **Phase:** 00
- **Supersedes / Superseded by:** none

## Context

`plan.md` section 110 requires UUID/UUIDv7 identifiers and forbids exposing
sequential identifiers publicly, to reduce enumeration risk and allow
distributed creation. The phase file repeats this and adds that public APIs
never expose sequential identifiers.

Random UUIDv4 primary keys carry a known cost in PostgreSQL: random insertion
order fragments B-tree indexes and inflates write amplification on high-volume
tables such as `audit_events`, `stock_movements`, and `outbox_events`.
UUIDv7 embeds a millisecond timestamp in its high bits, so keys are
time-ordered and insertions are close to append-only.

## Decision

All application entity primary keys are UUIDv7, stored in PostgreSQL as native
`uuid`. Identifiers are strings in every public contract.

Generation is centralized behind an `IdentityGenerator` port so that tests can
inject a deterministic sequence and so a future move to a database-side
generator is a single-adapter change.

Exceptions, which must never appear in a public contract:

- Framework-internal tables that Laravel owns and that no API exposes.
- Append-only ledger sequence columns used strictly for ordering within a
  partition, which are internal and never returned.

A UUIDv7 timestamp is not a secret, but it is metadata: it reveals record
creation time to anyone holding the identifier. Where creation time is itself
sensitive and the identifier is shared outside the trust boundary, the owning
phase must record that exposure in the data-classification entry.

## Consequences

### Positive

- Time-ordered keys keep index locality close to sequential inserts.
- No enumeration of records by incrementing an integer.
- Identifiers can be generated by the application, by a worker, or by a client
  draft without a round trip.

### Negative / accepted cost

- 16 bytes per key instead of 8; larger indexes and larger foreign keys.
- UUIDs are harder for humans to read in support conversations; runbooks must
  rely on search rather than recall.
- Creation-time leakage as described above.

### Risks and their mitigations

| Risk | Mitigation |
| --- | --- |
| A developer uses `Str::uuid()` (v4) by habit | Static analysis rule plus a unit test asserting generated identifiers are version 7 and monotonic within a millisecond batch |
| Clock skew produces out-of-order keys | UUIDv7 ordering is a performance property, never a correctness property; no invariant depends on key ordering |
| Sequential identifier leaks through a serializer | Contract tests assert identifier fields match the UUID pattern |

## Alternatives considered

| Alternative | Why rejected |
| --- | --- |
| `bigserial` primary keys | Enumerable when exposed; `plan.md` section 110 forbids it |
| UUIDv4 | Random insertion order fragments indexes on the highest-volume tables |
| ULID | Equivalent ordering benefit but not a native PostgreSQL type; UUIDv7 is standard and stores as `uuid` |
| Internal `bigserial` plus external UUID | Two identifiers per row, a join or lookup on every external reference, and a persistent risk of exposing the wrong one |

## Migration and rollback impact

Forward: initial. No table exists with a different key strategy.

Rollback: changing the key type of a populated table is a full rewrite with
foreign-key churn. Treat this decision as effectively irreversible after the
first production data load.

## Verification

- Unit test: generated identifiers are UUID version 7 and non-decreasing.
- Contract test: every identifier field in the OpenAPI document matches the UUID
  pattern and no field is an integer identifier.
- Migration convention check: new primary keys are `uuid`.

## Review requirement

Engineering, PostgreSQL consistency owner, security.
